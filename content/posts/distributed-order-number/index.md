前两篇聊了[通用的分布式 ID 生成方案]({{< relref "/posts/distributed-uid-design/index.md" >}})和[用户 UID 的设计]({{< relref "/posts/distributed-user-uid/index.md" >}})。订单号看起来只是“又一个 ID”，但它的约束比前两者都多：

- 它要**给人看**：用户在订单详情页看到它，打电话给客服时要能一个字一个字报出来；
- 它要**交给第三方**：支付渠道、物流公司、发票系统都会存它，而且各家对格式有自己的限制；
- 它要**能路由**：订单表通常按用户分库分表，但客服、支付回调手上往往只有订单号；
- 它**不能泄露信息**：订单量是最敏感的经营数据之一。

这篇文章就围绕这几个约束，一步步设计一个订单号。

---

## 先避开几个常见的坑

在讲怎么设计之前，先看看几种常见但有问题的做法。

**1. 数据库自增**

`ORDER_ID = 10086`。最大的问题是**泄露订单量**：竞争对手早上下一单、晚上下一单，两个订单号一减，就知道你一天卖了多少单。分库分表之后，自增也没法保证全局唯一。

**2. 时间戳 + 随机数**

`20261106143025` + 4 位随机数。看起来很合理，但同一秒内只有 1 万个随机数可选。根据生日悖论，同一秒内只要有约 $\sqrt{2 \ln 2 \cdot 10^4} \approx 118$ 个订单，发生重复的概率就超过 50%。大促时一秒几千单，重复几乎是必然的。

**3. 时间戳 + 用户 ID**

`20261106143025` + `UID`。同一用户同一秒下两单（比如购物车拆单）会重复；而且等于把用户 UID 直接暴露在了订单号里，拿到订单号就能反查用户。

**4. 直接用 UUID**

全局唯一没问题，但 32 个十六进制字符既没法在电话里报给客服，也不满足部分支付渠道“纯数字”或长度的要求。

---

## 订单号要满足哪些约束

把前面的需求整理一下：

| 约束 | 具体要求 |
| --- | --- |
| 全局唯一 | 底线 |
| 长度和字符集 | 能被各个支付渠道接受。微信支付的商户订单号 `out_trade_no` 要求 6～32 位，支付宝一般为最长 64 位（以各渠道最新官方文档为准）。**纯数字、不超过 32 位**最保险 |
| 可读 | 客服能电话报号，用户能手动输入；最好能发现输错 |
| 可路由 | 只凭订单号就能算出订单在哪个分片 |
| 不泄露订单量 | 不能从订单号推算出一天的下单量 |
| 带时间信息 | 客服一眼能看出下单日期；按月归档、冷热分离时可以直接定位 |
| 趋势递增 | 作为索引时写入友好 |

---

## 一个可行的结构

综合这些约束，我们可以设计一个 21 位的纯数字订单号：

```text
  261106     01      38462951      0423      6
 ────────   ────   ────────────   ──────   ────
   日期      业务     打散的序号      分片    校验位
  (6 位)   (2 位)     (8 位)       (4 位)   (1 位)
```

逐段解释每一部分的作用。

### 日期（6 位）：`yyMMdd`

- 客服一眼就能看出订单是哪天下的，用户回忆订单时也方便；
- 订单表如果按月分表或做冷热归档，可以直接从订单号里取出月份，路由到对应的归档表，不需要额外的查询；
- 订单号整体按日期趋势递增，对索引友好。

注意要**固定时区**生成日期，比如统一用北京时间。如果多地域部署的服务各自用本地时区，同一时刻生成的订单号日期会不一致，跨零点时还可能出现“明天的订单比今天的订单先生成”的情况。

日期本身确实暴露了下单时间，但这个信息在订单详情页、小票上本来就是公开的，可以接受。

### 业务类型（2 位）

区分普通订单、充值订单、退款单、售后单等。客服和对账人员看到前几位就知道这是什么单，排查问题时很省事。2 位可以容纳 100 种类型，一般足够。

### 打散的序号（8 位）

这是保证唯一性的核心。每天从 0 开始的递增序号，单日容量 1 亿单。

序号的来源可以用[第一篇]({{< relref "/posts/distributed-uid-design/index.md" >}})里讲的**号段模式**：以 `order:261106` 作为 `biz_tag`，每个服务实例一次领取一段序号缓存在本地，数据库压力很小。

但**序号不能直接放进订单号**，否则又回到了“两个订单号一减就知道订单量”的问题。所以要先用一个带密钥的置换函数把它打散，做法和上一篇[生成用户展示号]({{< relref "/posts/distributed-user-uid/index.md" >}})一样：Feistel 网络 + cycle walking，把 `[0, 1亿)` 里的序号一一映射到 `[0, 1亿)` 里的另一个数。置换是一一对应的，所以序号不重复，打散后的结果也一定不重复；而没有密钥的人看不出规律。

> 如果用 Redis 的 `INCR` 来生成每日序号，要特别注意持久化：Redis 宕机后如果丢了最近的数据，计数器会回退，接着就会生成重复的订单号。无论用什么方式，订单表上的 `order_no` 唯一索引都是最后一道防线，不能省。

### 分片位（4 位）：嵌入用户的“基因”

订单表一般按买家 UID 分片，这样“我的订单”只需要查一个分片。但客服查单、支付回调时只有订单号，这时就要用到[上一篇]({{< relref "/posts/distributed-user-uid/index.md" >}})讲过的**基因法**：

```text
分片位 = uid % 1024，格式化为 4 位数字（0000～1023）

于是：shard(订单号) = 分片位 = uid % 1024 = shard(uid)
```

无论按 UID 查还是按订单号查，都能算出同一个分片，不需要额外的映射表。这里按 1024 个逻辑分片设计，早期可以映射到少量物理库，以后扩容只改映射关系，订单号本身不用动。

### 校验位（1 位）

用 [Luhn 算法](https://en.wikipedia.org/wiki/Luhn_algorithm)（银行卡号的最后一位就是这么算的）对前面 20 位计算出一位校验位。它能发现**所有单个数字输错**，以及绝大多数**相邻两位颠倒**的情况（只有 `09` 和 `90` 互换检测不出来）。

用户在客服页面、售后表单里手动输入订单号时，前端或网关先校验一下，输错了直接提示，而不是拿着一个不存在的订单号去数据库里查一遍，还让用户以为“系统找不到我的订单”。

## 实现（Go）

```go
package orderno

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/binary"
	"errors"
	"fmt"
	"strconv"
	"time"
)

const (
	seqDomain = 100_000_000 // 8 位序号，每天最多 1 亿单
	shards    = 1024        // 逻辑分片数

	halfBits = 14 // Feistel 在 2^28 空间上置换，左右各 14 位
	halfMask = 1<<halfBits - 1
	rounds   = 4

	length = 21
)

var (
	loc = time.FixedZone("CST", 8*3600) // 固定用北京时间生成日期

	ErrSeqExhausted = errors.New("orderno: daily sequence exhausted")
	ErrInvalid      = errors.New("orderno: invalid order number")
)

// Build 生成订单号：日期(6) + 业务类型(2) + 打散的序号(8) + 分片位(4) + 校验位(1)
func Build(key []byte, t time.Time, bizType int, seq uint32, uid int64) (string, error) {
	if bizType < 0 || bizType > 99 {
		return "", fmt.Errorf("orderno: bad biz type %d", bizType)
	}
	if seq >= seqDomain {
		return "", ErrSeqExhausted
	}
	date := t.In(loc).Format("060102")
	payload := fmt.Sprintf("%s%02d%08d%04d", date, bizType, shuffle(key, date, seq), uid%shards)
	return payload + string(luhn(payload)), nil
}

// Shard 校验订单号并返回其所在的逻辑分片
func Shard(no string) (int, error) {
	if len(no) != length || !isDigits(no) || luhn(no[:length-1]) != no[length-1] {
		return 0, ErrInvalid
	}
	return strconv.Atoi(no[16:20])
}

// shuffle 把 [0, seqDomain) 内的序号一一映射到同一区间内的另一个数。
// 以日期参与密钥派生，每天的打散规律都不一样。
func shuffle(key []byte, date string, seq uint32) uint32 {
	x := seq
	for { // cycle walking：落在区间外就继续置换
		x = permute(key, date, x)
		if x < seqDomain {
			return x
		}
	}
}

// permute 是 [0, 2^28) 上的一个双射（Feistel 网络）
func permute(key []byte, date string, x uint32) uint32 {
	l, r := x>>halfBits, x&halfMask
	for i := 0; i < rounds; i++ {
		l, r = r, l^roundFunc(key, date, i, r)
	}
	return l<<halfBits | r
}

func roundFunc(key []byte, date string, round int, x uint32) uint32 {
	mac := hmac.New(sha256.New, key)
	mac.Write([]byte(date))
	var buf [5]byte
	buf[0] = byte(round)
	binary.BigEndian.PutUint32(buf[1:], x)
	mac.Write(buf[:])
	return binary.BigEndian.Uint32(mac.Sum(nil)) & halfMask
}

// luhn 计算 Luhn 校验位
func luhn(s string) byte {
	sum, double := 0, true // 追加校验位后，payload 的最右一位处于“需要加倍”的位置
	for i := len(s) - 1; i >= 0; i-- {
		d := int(s[i] - '0')
		if double {
			if d *= 2; d > 9 {
				d -= 9
			}
		}
		sum += d
		double = !double
	}
	return byte('0' + (10-sum%10)%10)
}

func isDigits(s string) bool {
	for i := 0; i < len(s); i++ {
		if s[i] < '0' || s[i] > '9' {
			return false
		}
	}
	return true
}
```

几点说明：

- 序号空间是 1 亿，Feistel 在 $2^{28}$（约 2.68 亿）上置换，平均约 $2^{28} / 10^8 \approx 2.7$ 次置换就能落回区间内，开销可以忽略；
- 日期参与了轮函数，相同的序号在不同日期打散的结果不同，避免“每天第 1 单的订单号尾数都一样”；
- 密钥要像其他密钥一样妥善保管，泄露后别人就能从订单号还原出当天的订单序号。

## 一个订单，不止一个号

上面设计的是**订单号**。真实的交易系统里，围绕一个订单往往还有好几种单号，它们**不应该共用同一个号**。

### 订单号 ≠ 支付单号

一个订单可能会支付多次：第一次支付超时，用户换了一种支付方式重新支付；或者支付渠道要求订单关闭后重新发起时必须换一个新的商户订单号。

所以建议订单和支付拆成两张表：一个订单号对应多条**支付单**记录，每次向支付渠道发起支付都生成一个新的支付单号，传给渠道的 `out_trade_no` 用的是支付单号。支付单号可以沿用同样的结构，只是业务类型位不同，分片位与订单一致，这样支付回调过来也能直接路由到同一个分片。

退款单号同理：一个订单可以部分退款多次，每次退款都应该有独立的退款单号。

### 拆单：父订单与子订单

用户在购物车里一次结算了三个商家的商品，通常会拆成一个**父订单**（对应用户的一次支付）和三个**子订单**（分别由三个商家履约）。子订单号应当和父订单使用**相同的分片位**，保证同一次购买的数据落在同一个分片，查询和事务都不需要跨库。

### 卖家视角：异构索引

订单表按买家 UID 分片，买家查“我的订单”很高效。但商家要查“我店铺的所有订单”时，订单分散在所有分片上，总不能每次都扫全部 1024 个分片。

常见做法是建一份**按卖家维度的异构索引**：通过订阅 binlog（如 Canal）把订单数据同步到一份按卖家 ID 分片的库，或者同步到 Elasticsearch 里。买家维度和卖家维度各查各的，互不干扰。代价是两份数据之间有短暂的延迟，商家后台一般可以接受。

## 幂等：防止重复下单

订单号还有一个常被忽略的作用：**防止重复下单**。用户网络不好连续点了两次“提交订单”，或者客户端超时后自动重试，如果每次请求都在服务端新生成订单号，就会产生两笔订单。

常见做法：

1. 用户进入确认订单页时，服务端先生成一个**下单令牌**（可以就是预先生成的订单号）返回给客户端；
2. 提交订单时带上这个令牌，客户端重试也使用同一个；
3. 服务端用令牌做幂等判断：订单表上 `order_no` 的唯一索引天然可以拦住重复插入，捕获唯一键冲突后返回已经创建好的那笔订单即可。

这样即使请求重复到达，也只会产生一笔订单。

## 小结

一个好的订单号，是在多个约束之间找到的平衡点：

| 段 | 解决的问题 |
| --- | --- |
| 日期 | 可读、按时间归档、趋势递增 |
| 业务类型 | 一眼区分单据类型 |
| 打散的序号 | 全局唯一，且不泄露订单量 |
| 分片位 | 只凭订单号就能路由到分片 |
| 校验位 | 发现手动输入错误 |

再加上几条原则：

1. **纯数字、不超过 32 位**，兼容主流支付渠道；
2. **订单号、支付单号、退款单号各自独立**，不要一个号用到底；
3. **子订单继承父订单的分片位**，卖家维度用异构索引；
4. **唯一索引是最后一道防线**，生成算法再可靠也不能省；
5. **用订单号做下单幂等**，从源头避免重复订单。

这套结构不是唯一的答案，位数可以按业务规模调整：日订单量小的可以缩短序号，分片少的可以缩短分片位。但它背后的思路是通用的：**先列出订单号要满足的约束，再给每个约束分配一段位置。**
