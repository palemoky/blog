在[订单号设计]({{< relref "/posts/distributed-order-number/index.md" >}})那篇文章的最后，提到了用订单号来防止重复下单。这其实只是幂等的一个特例。在分布式系统里，幂等几乎无处不在：支付回调、消息消费、接口重试、定时任务……只要有“重试”，就必须有幂等。

这篇文章就系统地聊一聊：重复请求从哪里来，幂等有哪些实现方式，以及实践中容易踩的坑。

---

## 什么是幂等

数学上，如果一个函数满足

$$
f(f(x)) = f(x)
$$

就称它是幂等的：执行一次和执行多次，效果相同。比如取绝对值 $|\,|x|\,| = |x|$。

放到系统里，幂等的意思是：**同一个请求执行一次和执行多次，对系统状态产生的影响是一样的。**

注意，这里说的是**对状态的影响**一样，而不是返回值一样。比如 HTTP 的 `DELETE /orders/123`，第一次返回 `204`，第二次可能返回 `404`，但订单都已经被删除了，状态没有区别，所以 `DELETE` 是幂等的。

HTTP 规范（[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#name-idempotent-methods)）里对方法的语义有明确定义：

| 方法 | 安全（不改变状态） | 幂等 |
| --- | --- | --- |
| `GET`、`HEAD`、`OPTIONS` | 是 | 是 |
| `PUT`、`DELETE` | 否 | 是 |
| `POST`、`PATCH` | 否 | 否 |

这只是规范层面的约定。你的 `PUT` 接口实现得是否真的幂等，还得看代码怎么写。而下单、支付这类最关键的操作，偏偏都是 `POST`。

## 重复请求从哪里来

在单机程序里，调用一个函数要么成功、要么失败。但在分布式系统里，一次网络调用有**三种结果**：成功、失败，以及**不知道**。

请求超时了，你并不知道是请求没送到、对方处理到一半挂了，还是对方已经处理成功、只是响应在路上丢了。面对“不知道”，唯一的办法就是重试。而一旦重试，就可能重复。

重复请求的来源比想象中多：

| 来源 | 场景 |
| --- | --- |
| 用户 | 网络卡顿时连点“提交”按钮，或者刷新页面重新提交表单 |
| 客户端 | SDK、App 在超时后自动重试 |
| 网关、负载均衡 | 上游超时后转发给另一个实例重试 |
| RPC 框架 | 很多框架默认开启超时重试 |
| 消息队列 | 消费者处理完、还没提交位点（offset）就挂了，重启后这条消息会再投递一次 |
| 第三方回调 | 支付渠道在收到你的“成功”应答前，会按一定间隔反复推送通知 |
| 定时任务 | 任务执行到一半失败，被调度系统重新拉起 |

消息队列通常只承诺“至少一次”（at-least-once）投递。业界常说的“恰好一次”（exactly-once），在端到端的业务层面，实际上是这样实现的：

$$
\text{恰好一次} = \text{至少一次} + \text{幂等}
$$

重试保证“不丢”，幂等保证“不重”，两者缺一不可。所以说，**幂等是重试的另一半**。

## 实现幂等的几种方式

### 1. 让操作本身天然幂等

最好的幂等是不需要额外机制的幂等。很多时候，只要换一种写法，操作就从非幂等变成了幂等。

```sql
-- 非幂等：执行两次就扣了两次
UPDATE account SET balance = balance - 100 WHERE id = 1;

-- 幂等：执行多少次结果都一样
UPDATE user SET nickname = 'palemoky' WHERE id = 1;
```

**绝对赋值天然幂等，相对增减不幂等。** 查询、按主键删除、覆盖式写入、“开关”类设置（设为已读、设为启用）也都是天然幂等的。

但扣款、加库存、发积分这类“增量”操作没法改成绝对赋值，就需要下面的手段了。

### 2. 唯一约束

利用数据库的唯一索引，让重复的插入直接失败：

```sql
CREATE TABLE orders (
    id       BIGINT PRIMARY KEY,
    order_no VARCHAR(32) NOT NULL,
    -- ...
    UNIQUE KEY uk_order_no (order_no)
);
```

客户端在提交前就拿到订单号（下单令牌），重试时带上同一个订单号。第二次插入会触发唯一键冲突，服务端捕获这个错误，查出第一次创建的订单返回即可。

这是最简单、最可靠的方式，因为**唯一性由数据库保证，不存在并发漏洞**。适用于“创建”类操作：下单、注册、创建支付单、记一条流水。

### 3. 状态机 + 条件更新

对于“修改”类操作，可以借助业务状态机，把状态检查和状态变更放在同一条 SQL 里：

```sql
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE order_no = '261106013332941500010'
  AND status = 'UNPAID';
```

第一次执行影响 1 行，订单变为已支付；之后重复执行，因为状态已经不是 `UNPAID`，影响 0 行。**根据影响行数，就能判断是不是重复请求。**

这正是处理支付回调的标准做法：

1. 收到回调后，先验签；
2. 用条件更新把订单从“待支付”改为“已支付”；
3. 影响 1 行，说明是第一次处理，继续执行后续业务（发货、加积分）；
4. 影响 0 行，说明已经处理过了，**直接返回成功应答**。

第 4 步很关键：重复的回调也要返回成功。如果返回失败，支付渠道会认为你没收到，继续推送通知。

同样的思路还有**乐观锁**：给记录加一个 `version` 字段，更新时带上 `WHERE version = ?`，只有版本号匹配才能更新成功。

### 4. 幂等键 + 幂等记录表

前面几种方式都依赖业务本身的特点。如果想要一个**通用的**幂等机制，比如让一组对外 API 都支持安全重试，就需要幂等键（Idempotency Key）。

做法是：客户端为每个“逻辑请求”生成一个唯一的幂等键（通常是 UUID），放在请求头里；重试时使用同一个键。服务端用一张表记录每个幂等键的处理结果。

这已经是业界的通行做法。比如 [Stripe](https://docs.stripe.com/idempotency) 的 API 就支持 `Idempotency-Key` 请求头：它会保存第一次请求的状态码和响应体，之后相同幂等键的请求直接返回保存的结果；幂等键保存至少 24 小时。IETF 也有一份[草案](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)在尝试把这个请求头标准化（截至目前仍是草案，还不是 RFC）。

一张最简单的幂等记录表：

```sql
CREATE TABLE idempotency_record (
    idem_key    VARCHAR(128) PRIMARY KEY,  -- 幂等键，建议带上用户维度，如 "uid:key"
    fingerprint CHAR(64)     NOT NULL,     -- 请求参数的哈希，防止同一个键被用在不同请求上
    response    BLOB,                      -- 第一次处理的响应，用于重放
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_created_at (created_at)        -- 方便按时间清理过期记录
);
```

几个设计要点：

- **幂等键要带上用户维度**：幂等键由客户端生成，不能完全信任。如果只用客户端传来的键做主键，不同用户的键碰撞，或者恶意用户猜测别人的键，就可能拿到别人的响应。用 `uid:key` 这样的组合就能避免；
- **校验请求指纹**：同一个幂等键，第二次请求的参数却和第一次不一样，这通常是客户端的 bug。此时应当拒绝请求，而不是返回第一次的结果，否则客户端会误以为新的请求成功了。上面提到的 IETF 草案建议对这种情况返回 `422`；
- **过期时间要覆盖重试窗口**：幂等记录不可能永久保存，但保存时间必须长于客户端可能重试的最长时间。记录过期后再来一次重试，就会被当成新请求执行。

## 关键细节：幂等记录和业务必须在同一个事务里

幂等记录表最容易写错的地方，是**幂等记录和业务操作不在同一个事务里**。

先看一种常见的错误写法：

```text
1. 查询幂等记录，不存在
2. 执行业务（扣款）
3. 写入幂等记录
```

这里有两个问题：

- **并发漏洞**：两个相同的请求同时到达，第 1 步都查不到记录，于是都去扣款了。这是典型的“先检查后执行”（check-then-act）竞态；
- **崩溃漏洞**：第 2 步成功了，进程在第 3 步之前挂了。客户端重试时查不到幂等记录，又扣了一次款。

正确的做法是：**先插入幂等记录占位，并且和业务操作放在同一个本地事务里。**

```go
package idem

import (
	"context"
	"crypto/sha256"
	"database/sql"
	"encoding/hex"
	"errors"

	"github.com/go-sql-driver/mysql"
)

var ErrKeyReused = errors.New("idem: key reused with a different request")

// Do 在同一个本地事务里完成：占位 → 执行业务 → 记录响应。
// key 应当已经带上用户维度（如 "uid:key"）；fn 执行业务逻辑，返回要缓存的响应。
func Do(ctx context.Context, db *sql.DB, key string, reqBody []byte,
	fn func(tx *sql.Tx) ([]byte, error)) ([]byte, error) {

	sum := sha256.Sum256(reqBody)
	fingerprint := hex.EncodeToString(sum[:])

	// 多个相同 key 的请求同时等待时，可能触发 InnoDB 死锁（见下文）。
	// 死锁时事务已被整体回滚，重试是安全的
	for attempt := 1; ; attempt++ {
		resp, err := doOnce(ctx, db, key, fingerprint, fn)
		if !isDeadlock(err) || attempt == 3 {
			return resp, err
		}
	}
}

func doOnce(ctx context.Context, db *sql.DB, key, fingerprint string,
	fn func(tx *sql.Tx) ([]byte, error)) ([]byte, error) {

	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return nil, err
	}
	defer tx.Rollback() // 提交之后再调用不会有副作用

	// 1. 占位。相同 key 的并发请求会阻塞在唯一键的锁上，直到前一个事务结束
	_, err = tx.ExecContext(ctx,
		`INSERT INTO idempotency_record (idem_key, fingerprint) VALUES (?, ?)`,
		key, fingerprint)
	if isDuplicateKey(err) {
		tx.Rollback()
		return replay(ctx, db, key, fingerprint) // 已经处理过，重放第一次的结果
	}
	if err != nil {
		return nil, err
	}

	// 2. 执行业务。失败则整个事务回滚，占位记录一起消失，客户端可以安全重试
	resp, err := fn(tx)
	if err != nil {
		return nil, err
	}

	// 3. 记录响应，和业务一起提交
	if _, err := tx.ExecContext(ctx,
		`UPDATE idempotency_record SET response = ? WHERE idem_key = ?`,
		resp, key); err != nil {
		return nil, err
	}
	if err := tx.Commit(); err != nil {
		return nil, err
	}
	return resp, nil
}

func replay(ctx context.Context, db *sql.DB, key, fingerprint string) ([]byte, error) {
	var fp string
	var resp []byte
	err := db.QueryRowContext(ctx,
		`SELECT fingerprint, response FROM idempotency_record WHERE idem_key = ?`,
		key).Scan(&fp, &resp)
	if err != nil {
		return nil, err
	}
	if fp != fingerprint {
		return nil, ErrKeyReused
	}
	return resp, nil
}

func isDuplicateKey(err error) bool {
	var me *mysql.MySQLError
	return errors.As(err, &me) && me.Number == 1062 // ER_DUP_ENTRY
}

func isDeadlock(err error) bool {
	var me *mysql.MySQLError
	return errors.As(err, &me) && me.Number == 1213 // ER_LOCK_DEADLOCK
}
```

这段代码借助了 InnoDB 的一个特性：两个事务插入相同的唯一键时，后一个会**阻塞等待**前一个事务结束。

- 如果前一个事务**提交**了，后一个插入会报唯一键冲突，于是走重放逻辑，返回第一次的结果；
- 如果前一个事务**回滚**了（业务失败），后一个插入会成功，相当于重新执行一次。

因为占位、业务、记录结果在同一个事务里，要么全部成功，要么全部消失，前面说的并发漏洞和崩溃漏洞都不存在了。

不过，这里有一个容易忽略的坑：**前一个事务回滚时，如果有多个请求同时在等，它们之间会发生死锁。** 等待者在检查唯一键冲突时持有的是共享锁，前一个事务回滚后，几个等待者都想把共享锁升级为排他锁去完成插入，互相等待对方释放，InnoDB 只能挑出其中一个成功，其余的报 `1213 Deadlock`。我在 MySQL 9.7 上实测：让第一个事务回滚，同时有 5 个请求在等待，10 轮下来 50 个等待的请求中有 40 个收到了死锁错误。好在流水表里每一轮都只有一条记录，**正确性没有问题，但客户端收到的是一个错误，而不是第一次的结果**。

所以 `Do` 在外层对死锁做了有限次数的重试：死锁时 InnoDB 已经把整个事务回滚了，重试一次，插入会遇到唯一键冲突，正常走重放逻辑。加上重试之后，同样的测试里所有等待的请求都拿到了同一个结果。

此外还有两点需要注意：

- **事务要短**：相同幂等键的重复请求会一直阻塞到前一个事务结束（MySQL 默认的锁等待超时是 50 秒）。业务逻辑里不要做慢查询，更不要在事务里调用外部服务；
- **业务失败要不要缓存**：上面的实现中，业务失败会回滚，重试时会重新执行。对于“余额不足”这类确定性失败，重新执行的结果也一样，问题不大；如果希望失败结果也能重放，就需要把失败结果单独提交到幂等记录里。

## 当业务涉及外部调用

上面的方案依赖“所有操作都在同一个本地事务里”。但很多业务绕不开外部调用，比如向支付渠道发起扣款。外部调用没法放进本地事务，这时就需要一个显式的**处理中**状态：

```text
PROCESSING ──▶ SUCCEEDED
           └──▶ FAILED
```

1. 先在一个短事务里插入幂等记录，状态为 `PROCESSING`，提交；
2. 调用外部服务；
3. 根据结果，把状态更新为 `SUCCEEDED` 或 `FAILED`，并记录响应。

相同幂等键的请求进来，看到 `PROCESSING` 就直接返回“处理中”（IETF 草案建议返回 `409 Conflict`），让客户端稍后再查，而不是再调用一次外部服务。

最难处理的是第 2 步**超时**的情况：外部调用到底成功了没有，不知道。这时**绝对不能直接标记为 `FAILED`**，否则客户端一重试，就可能真的扣了两次款。正确的做法是：

- **主动查询**：调用外部服务的查询接口（比如支付渠道的“查单”接口），确认真实结果后再更新状态；
- **把幂等传递下去**：调用外部服务时，也带上一个由自己生成、可以重复使用的唯一标识。比如向支付渠道发起支付时，传入的商户订单号就是[支付单号]({{< relref "/posts/distributed-order-number/index.md" >}})，渠道会根据它去重。这样即使重复调用，渠道那边也只会扣一次款。

**自己的接口幂等，并不代表整条调用链都幂等。** 每一个会产生副作用的下游调用，都要问一句：如果这一步被重试，会发生什么？

## 消息消费的幂等

消息队列是重复的“重灾区”。以 Kafka 为例：

- 生产者开启幂等（`enable.idempotence`）后，可以避免因**生产者重试**导致的消息重复写入；
- 但这管不到消费端：消费者处理完消息、还没提交 offset 就崩溃了，重启后同一条消息还会再消费一次；
- Kafka 的事务能实现“读取 - 处理 - 写回 Kafka”这一闭环内的恰好一次，但只要消费的结果写到了 Kafka 之外（比如写数据库、调接口），仍然需要业务自己保证幂等。

所以，**消费者必须按“消息一定会重复”来设计**。用什么做幂等依据？

- **优先用业务唯一键**，比如订单号、支付单号、流水号，结合前面的唯一约束或状态机；
- **谨慎依赖消息 ID**：生产者重试、重新发送时，同一个业务事件可能会产生不同的消息 ID，用消息 ID 去重会漏掉这类重复。

## 几个常见的误区

**1. 分布式锁 ≠ 幂等**

用 Redis 分布式锁把请求“串行化”，只能防止**并发**的重复请求，防不住**先后到达**的重复请求：第一个请求处理完释放了锁，第二个请求照样能拿到锁再执行一遍。锁还可能因为超时提前释放。锁可以作为辅助，但最终的判断必须落在唯一约束、状态机这类**持久化的状态**上。

**2. 用 Redis 存幂等记录，却和数据库操作分开**

Redis 写成功、数据库事务失败，或者反过来，都会出现不一致。而且 Redis 在故障切换时可能丢失最近的写入，幂等记录一丢，重复请求就被放行了。Redis 可以挡在前面做一层快速过滤，但**最后一道防线应该是和业务数据在同一个库里的唯一约束**。

**3. 防重复提交的令牌，删早了或删晚了**

常见的防重复提交方案：进入页面时发一个令牌，提交时校验并删除。问题在于删除的时机：

- **先删令牌，再执行业务**：业务失败了，令牌也没了，用户重试会被拒绝；
- **先执行业务，再删令牌**：两个并发请求可能都通过了校验。

令牌适合用来挡住“手抖连点”这类前端问题，但它本身不是完整的幂等方案。更稳妥的做法是像订单号那样，**让令牌本身成为业务数据的唯一键**。

**4. 重复请求返回错误**

检测到重复请求后，返回一个“请勿重复提交”的错误，看起来很合理，但对于自动重试的客户端来说，这等于告诉它“失败了”，它可能会走失败处理逻辑，甚至提示用户支付失败。**对于重复请求，正确的做法是返回第一次处理的结果。**

## 小结

幂等的核心思想只有一句话：**把“这个请求是否已经处理过”变成一个可以持久化、可以原子判断的状态。**

| 场景 | 推荐方式 |
| --- | --- |
| 能改写成绝对赋值 | 天然幂等，什么都不用加 |
| 创建类操作 | 业务唯一键 + 唯一约束 |
| 状态变更、支付回调 | 状态机 + 条件更新 |
| 通用 API 重试 | 幂等键 + 幂等记录表，和业务同一个事务 |
| 涉及外部调用 | `PROCESSING` 状态 + 超时后查询 + 向下游传递幂等标识 |
| 消息消费 | 按业务唯一键去重，假设消息一定会重复 |

最后记住几条原则：

1. **有重试就必须有幂等**，两者是一体的；
2. **最后一道防线是数据库的唯一约束**，锁和缓存都只是辅助；
3. **幂等判断和业务操作要原子**，避免“先检查后执行”；
4. **超时不等于失败**，结果未知时先查询，不要贸然重试或标记失败；
5. **重复请求返回第一次的结果**，而不是报错。
