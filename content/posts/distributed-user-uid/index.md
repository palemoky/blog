上一篇[分布式系统中的唯一 ID 设计]({{< relref "/posts/distributed-uid-design/index.md" >}})聊的是“怎么生成一个不重复的 ID”。但落到**用户**这个实体上，事情要复杂得多：

- 用户 UID 几乎会出现在系统的每一张表里，是全系统被引用最多的字段；
- 它往往是分库分表的分片键，决定了数据落在哪台机器上；
- 它会出现在主页链接、分享卡片、客服工单里，被外部看到；
- 一旦定下，**基本没有修改的可能**。

所以用户 UID 的设计，不只是选一个 ID 生成算法，更是在设计“一个用户在系统里如何被标识、被找到、被展示”。这篇文章就围绕这个问题展开。

---

## 一个用户，三层身份

很多系统早期的设计是：用户表一个自增主键，手机号唯一索引，登录时 `WHERE phone = ?`，完事。规模上来之后，通常会演变成三层身份分离的结构：

| 层次 | 例子 | 谁在用 | 是否可变 |
| --- | --- | --- | --- |
| **内部 UID** | `7262981345628160001` | 系统内部，所有表的外键 | 永不改变 |
| **展示号** | `385920174`、`@palemoky` | 用户之间，用于搜索、分享 | 可能允许修改 |
| **登录凭证** | 手机号、邮箱、第三方 openid | 登录、找回密码 | 可换绑、可解绑 |

核心原则只有一条：**内部 UID 只负责“标识”，不承载任何业务含义，也不直接暴露给用户。**

### 为什么不能用手机号/邮箱当 UID

这是最常见的反模式，问题在于：

1. **会变**：用户换手机号、换邮箱是常态。如果手机号是主键，换绑就意味着改全系统所有引用它的数据；
2. **会被回收**：运营商会把注销的手机号重新放号，新主人拿着这个号来注册，系统里却已经有“他”的账号了；
3. **是隐私数据**：手机号、邮箱属于个人信息，作为主键意味着它会出现在每一张表、每一条日志、每一个 MQ 消息里，脱敏和合规都无从谈起；
4. **一个人可能有多个**：用户想同时用手机号、邮箱、第三方账号登录，主键却只能有一个。

### 为什么内部 UID 不直接对外

内部 UID 通常是 Snowflake 或号段生成的 64 位整数，直接对外有几个问题：

- 太长，19 位数字没人记得住，也不好口头传达；
- 号段生成的 UID 是连续的，暴露了注册量，也方便被遍历；
- Snowflake 生成的 UID 可以反解出注册时间；
- 一旦暴露出去被外部系统引用，以后想换 ID 方案就彻底没机会了。

所以对外需要一个独立的**展示号**，后面会专门讲怎么生成。

## 登录凭证：身份映射表

把“用什么登录”和“你是谁”拆开，用一张映射表关联起来：

```sql
CREATE TABLE user_identity (
    id            BIGINT PRIMARY KEY,
    identity_type VARCHAR(16)  NOT NULL,   -- phone / email / wechat / apple / github ...
    identifier    VARCHAR(128) NOT NULL,   -- 手机号、邮箱、第三方平台的用户标识
    uid           BIGINT       NOT NULL,   -- 指向内部 UID
    credential    VARCHAR(255),            -- 密码哈希等，第三方登录可为空
    created_at    DATETIME     NOT NULL,
    UNIQUE KEY uk_identity (identity_type, identifier),
    KEY idx_uid (uid)
);
```

登录流程变成两步：先用 `(identity_type, identifier)` 查到 `uid`，再用 `uid` 去查用户的其他数据。这样设计之后：

- **多种登录方式**：一个 `uid` 对应多行记录，手机号、邮箱、微信都能登录同一个账号；
- **换绑**：只是改一行映射，用户的其他数据纹丝不动；
- **解绑与安全**：解绑最后一种登录方式前要做校验，否则用户会把自己锁在门外；
- **手机号二次放号**：检测到“这个号码长期未登录，又有人用它注册”时，可以要求额外验证，而不是直接登进旧账号。

### 第三方登录：注意标识的作用域

第三方平台给的用户标识，作用域往往不是全局的。以微信为例：

- **openid**：同一个用户在**不同应用**（公众号、小程序、App）里的 openid 是不同的；
- **unionid**：同一个开放平台账号下的多个应用，同一用户的 unionid 相同。

如果你的产品同时有 App 和小程序，却只存了 openid，就会出现同一个人在两端被识别成两个用户的情况。**能拿到 unionid 时，应该优先用 unionid 作为 identifier。** 其他平台也有类似的概念，接入时要先搞清楚它给的 ID 在什么范围内唯一。

## 分库分表：UID 作为分片键

用户量上来之后，用户相关的数据一般会按 UID 分片：`shard = uid % N`（或者对 UID 做哈希）。这样“查某个用户的所有数据”只需要访问一个分片。

但问题马上就来了：**登录时手上只有手机号，不知道 UID，该去哪个分片找？**

### 解法一：映射表单独分片

上面的 `user_identity` 表本身按 `identifier` 的哈希分片。登录时先按手机号路由到映射表的某个分片，查出 UID，再按 UID 路由到用户数据分片。多一次查询，但逻辑清晰，换绑也没问题。这是最通用的方案。

### 解法二：基因法

基因法的思路是：**让一个 ID 里“携带”另一个 ID 的分片信息**，使两者路由到同一个分片。

这个方法在用户体系里最经典的应用其实不是登录，而是**订单等用户附属数据**：订单表按 UID 分片，用户查“我的订单”时路由到自己的分片；但客服、支付回调手上只有订单号，怎么办？

做法是生成订单号时，把 UID 的低若干位“嫁接”到订单号的低位上：

```text
订单号 = [ 时间戳 | 机器 ID | 序列号 | uid 的低 10 位 ]

于是 order_id % 1024 == uid % 1024
```

这样无论按 UID 还是按订单号，都能算出同一个分片，不需要额外的映射表。

用在登录场景时要格外小心：如果把手机号的“基因”嵌进 UID，用户一换手机号，基因就对不上了。**基因只能取自永远不变的东西**，而手机号、邮箱都不满足这个条件，所以登录查找还是推荐用解法一。

### 给扩容留余地

不管用哪种方式，都建议**区分逻辑分片和物理分片**：

- 一开始就按 1024 个逻辑分片来路由（`uid % 1024`），基因法也嵌 10 位；
- 早期 1024 个逻辑分片可能只映射到 4 个物理库上；
- 扩容时只需要迁移部分逻辑分片、修改“逻辑 → 物理”的映射，路由规则和已经生成的 ID 都不用动。

如果一开始只嵌了 2 位基因（只能支持 4 个分片），将来要扩到 16 个分片时，所有存量数据的路由都会出问题，这几乎无法挽回。

## 展示号：短、不连续、可读

展示号是用户看到、搜索、口头告诉别人的号码，一般是 8～10 位数字。对它的要求是：

1. **唯一**，且和 UID 一一对应；
2. **短**，好记好输入；
3. **不连续、不可推测**，不能暴露注册量，也不能被轻易遍历；
4. **能过滤“靓号”**，比如 `88888888`、`12345678`，这些号应该留给运营，而不是随机发给普通用户。

常见的生成方式有两种。

### 方式一：预生成号池

离线生成一大批号码（比如 1 亿到 9.99 亿之间的全部号码），**过滤掉靓号单独存放**，剩下的打乱顺序写入号池表。用户注册时从号池里取一个，用完再补充下一批。

优点是直观、可控，靓号规则可以随时调整；缺点是号池本身要存储和维护，分配时要处理并发取号（通常结合上一篇提到的号段模式，每个服务实例一次领一批）。

### 方式二：可逆置换（格式保留加密）

更优雅的做法是：内部维护一个连续递增的序号（0, 1, 2, ...），用一个**带密钥的置换函数**把它映射到展示号空间里。置换函数是一一映射，所以序号不重复，展示号就一定不重复；而没有密钥的人看不出相邻展示号之间的规律。

下面用 Feistel 网络在 30 位空间（约 10.7 亿）上构造置换，再用 **cycle walking** 把结果收敛到 `[0, 9 亿)`，最后加上 1 亿，得到 9 位数的展示号：

```go
package displayid

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/binary"
	"errors"
)

const (
	halfBits = 15
	halfMask = 1<<halfBits - 1 // 30 位空间拆成左右各 15 位
	rounds   = 4

	domain = 900_000_000 // 可用的展示号数量
	base   = 100_000_000 // 展示号从 100000000 开始，保证是 9 位数
)

var ErrExhausted = errors.New("displayid: sequence exhausted")

// round 是 Feistel 的轮函数，用 HMAC-SHA256 做伪随机函数
func round(key []byte, r int, x uint32) uint32 {
	var buf [5]byte
	buf[0] = byte(r)
	binary.BigEndian.PutUint32(buf[1:], x)

	mac := hmac.New(sha256.New, key)
	mac.Write(buf[:])
	return binary.BigEndian.Uint32(mac.Sum(nil)) & halfMask
}

// permute 是 [0, 2^30) 上的一个双射
func permute(key []byte, x uint32) uint32 {
	l, r := x>>halfBits, x&halfMask
	for i := 0; i < rounds; i++ {
		l, r = r, l^round(key, i, r)
	}
	return l<<halfBits | r
}

// Encode 把序号 seq ∈ [0, domain) 映射为一个 9 位展示号
func Encode(key []byte, seq uint32) (uint32, error) {
	if seq >= domain {
		return 0, ErrExhausted
	}
	// cycle walking：结果落在 domain 之外就继续置换，直到落回来
	x := seq
	for {
		x = permute(key, x)
		if x < domain {
			return x + base, nil
		}
	}
}
```

为什么 cycle walking 能保证唯一？`permute` 是 $2^{30}$ 个数上的一个置换，从 `seq` 出发反复置换，一定会沿着它所在的环走回 `seq` 本身，所以必然会在某一步落回 `[0, domain)` 内；而不同的 `seq` 在同一个环上走到的“下一个落在范围内的点”也一定不同。由于 9 亿占 $2^{30}$ 的 84%，平均只需 $2^{30} / (9 \times 10^8) \approx 1.19$ 次置换就能落回来，几乎没有性能开销。

靓号过滤也很简单：生成展示号后检查是否命中靓号规则，命中就把这个序号标记为“保留”，然后用下一个序号重新生成。

```go
// IsPretty 判断是否为靓号：包含 4 个及以上连续相同或连续递增/递减的数字
func IsPretty(n uint32) bool {
	var d []int
	for ; n > 0; n /= 10 {
		d = append([]int{int(n % 10)}, d...)
	}
	same, up, down := 1, 1, 1
	for i := 1; i < len(d); i++ {
		same = ifThen(d[i] == d[i-1], same+1, 1)
		up = ifThen(d[i] == d[i-1]+1, up+1, 1)
		down = ifThen(d[i] == d[i-1]-1, down+1, 1)
		if same >= 4 || up >= 4 || down >= 4 {
			return true
		}
	}
	return false
}

func ifThen(cond bool, a, b int) int {
	if cond {
		return a
	}
	return b
}
```

实际业务里的靓号规则会复杂得多（`520`、`1314`、`AABB` 结构、生日格式等），规则放到配置里，随时可以调整。

几点注意：

- **密钥是机密**：泄露之后，任何人都能从展示号反推注册顺序；
- **展示号要落库**：`user.display_id` 加唯一索引，查询时直接走索引，不需要每次计算，也不依赖解密；
- **这不是安全边界**：它只是让遍历和推测变难，接口的鉴权一样都不能少。

### 用户自定义 ID

很多产品还允许用户设置一个字母数字组成的自定义 ID（类似 `@palemoky`）。它本质上是另一种展示号，需要额外处理：

- **大小写和形近字符**：`Palemoky` 和 `palemoky` 是否算同一个？`l` 和 `1`、`O` 和 `0` 是否需要防冒充？一般做法是存一个规范化（小写、去除易混淆字符）后的字段，在它上面建唯一索引；
- **保留词**：`admin`、`support`、`official`、品牌词等提前保留；
- **修改频率**：允许修改的话，要限制频率，并且旧 ID 要冷冻一段时间才能被别人使用，否则会被人抢注冒充。

## UID 的生命周期

### 永不复用

用户注销后，**内部 UID 绝不回收**。原因很简单：系统里总会有你没清理干净的引用——日志、离线数仓、缓存、第三方系统里存的 UID、甚至用户之间的聊天记录。一旦把旧 UID 分给新用户，新用户可能看到旧用户的数据，或者继承了旧用户的权限和黑名单记录。

64 位的 UID 空间足够大，不值得为了省号段冒这个风险。展示号如果要回收，也一定要有足够长的冷冻期。

### 注销：删数据，留墓碑

注销账号时，按照个人信息保护的相关要求，需要删除或匿名化用户的个人信息：手机号、邮箱、昵称、头像等。但 UID 本身建议保留一条**墓碑记录**（状态标记为已注销），这样：

- 历史订单、评论等数据里的 UID 引用不会变成悬空指针，可以统一展示为“已注销用户”；
- 防止同一个 UID 被误分配；
- 审计和对账时有据可查。

### 账号合并

用户可能先用手机号注册了一个账号，后来又用微信注册了另一个，然后要求合并。不要试图修改全系统里旧 UID 的所有引用，那几乎做不到。常见做法是：

- 选定一个**主 UID**，把另一个账号的登录凭证（`user_identity` 记录）迁移到主 UID 名下；
- 被合并的账号标记为 `merged_into = 主 UID`；
- 核心资产（余额、会员等）按业务规则迁移，其余历史数据保持原样，查询时通过 `merged_into` 做一次跳转。

## 其他细节

- **前端精度**：64 位 UID 在 JavaScript 里会丢精度，接口一律用字符串返回，上一篇有详细说明；
- **多地域部署**：如果用户数据需要按地域存储（比如合规要求数据不出境），可以在 UID 里预留几位表示用户的归属地域，网关看到 UID 就知道该路由到哪个地域，不需要再查一次全局表；
- **日志和埋点**：日志里只打 UID，不打手机号、邮箱，排查问题时通过 UID 关联，这比事后做日志脱敏省事得多。

---

## 小结

一套合理的用户 UID 体系，可以概括成下面几条：

1. **内部 UID**：64 位、全局唯一、不含业务含义、不对外暴露、永不修改、永不复用；
2. **登录凭证**：通过身份映射表关联到 UID，支持多种登录方式和换绑；第三方登录注意 ID 的作用域；
3. **分片**：按 UID 分片，附属数据用基因法对齐分片；一开始就按足够多的逻辑分片设计；
4. **展示号**：短、不连续、过滤靓号，可以用号池或可逆置换生成，并单独落库；
5. **生命周期**：注销留墓碑，合并做跳转，不改历史引用。

说到底，用户 UID 是系统里最“长寿”的数据，它会比你现在写的每一行代码都活得更久。前期多想一步，比后期迁移数据要便宜太多。
